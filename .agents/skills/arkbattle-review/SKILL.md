# 代码审查

默认只审查，不修改代码；修改需要用户明确授权。

重点检查几项：

1. **防御**：根据数据的信任边界、领域约束和实际可达状态判断是否需要防御，结合实际风险，不为凭空构造的异常情况增加复杂度。
2. **校验**：在真正的数据入口或信任边界完成校验与合法构造；内部信任已由类型和领域契约建立的不变量，不重复校验。领域操作或回调改变状态后，仍需按业务续执行条件读取并判断最新状态。
3. **可读性与必要性**：以已确认的业务语义为依据，沿完整调用链和数据流审查实现是否直接清晰，比较更简单的表达。质疑职责拆分、函数抽取、包装和间接跳转的必要性，不局限于局部代码，也不按复用次数或代码行数机械判断抽象。当前实现、文档和测试均是待审材料，不能以相互一致证明设计合理。
4. **特例**：同类概念出现特例，就必须追查；追查后如果能找到真实的领域语义差异，就应该保留。

先核对当前代码、调用路径与相关文档，区分已确认的业务契约与可调整的工程设计。涉及契约改变或重要未决取舍时，转入架构讨论，不在复审中自行定案。

发现问题时给出代码位置、理由和简化建议；区分有证据的问题与待核实的判断，不强凑数量。复审以最新代码为准，不机械重复旧结论。
