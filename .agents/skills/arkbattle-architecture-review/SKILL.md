# 架构审查

默认只分析与提出方案，修改代码需用户明确授权。重大重构按领域契约是否改变判断。

1. **先理解语义，再权衡设计**：涉及原生机制时先核对事实，证据不足则使用 [arkbattle-native-research](../arkbattle-native-research/SKILL.md) 调查，再结合项目目标与约束权衡工程方案；不把原生实现当作必须照搬的结构。
2. **据此质疑当前实现**：以领域语义和项目目标为依据，沿上下游调用链、数据流和依赖审查整体职责、状态归属、接口与抽象是否合理、必要，比较更直接的设计，避免局限当前目录做出局部最优的决定。当前代码、文档和测试都是待审材料，不能用“现在如此”证明“应当如此”。
3. **明确决策并告知用户**：事实与既定约束足以判断的工程选择，直接给出方案及理由、影响；涉及未明确的业务语义、改变已确认的约定，或无法依据项目目标决定的重要取舍时，说明选项、代价和推荐方案，请用户决定。
