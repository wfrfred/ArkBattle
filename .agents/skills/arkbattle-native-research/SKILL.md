# 原生机制调查

1. **确定问题**：明确待核实的行为和条件，先查已有研究与 PRTS，记录仍缺少的证据。用户指定材料时直接核对；PRTS 是社区资料。
2. **按需选路径**：
   - 字段结构、取值、覆盖和内容引用：读[配置调查](references/configuration-workflow.md)，使用 `config.py`／`assets.py`。
   - 配置如何生效、触发条件、公式或执行顺序：读[客户端实现调查](references/client-workflow.md)，使用 `native.py`。
   两条路径可以独立完成，结论依赖另一类证据时再联查，不强制经过全部步骤。
3. **核实结论**：分清直接证实、推断和未知，注明来源版本与适用范围。配置存在不等于实际激活，有限样本无命中不能证明全局不存在；静态实现不等于运行时观测。证据足够即停止，重要歧义再做定向实验。
4. **归档结果**：记录证据、限制与项目影响，不自行修改实现或确定架构政策。项目代码和测试不能证明原生行为。

优先复用工具完成检索、统计、定位和提取；完整结果写文件，只读取必要摘要与片段。通用能力补入共享脚本，专用解码留在证据批次，避免反复编写同类脚本。

结果归入 `docs/research`：

- `cases/NN-topic.md`：集中维护同一问题的结论、证据和未决项；后续调查更新原案例，新增案例更新索引。
- `evidence/topic-YYYYMMDD/`：保存必要的 `provenance`／`result`、摘录与专用解码。README 写来源版本／指纹、选择范围、复跑命令和限制；保留历史原件，缺失信息不补造。
- `archive.py --batch <批次目录>` 整理本批清单；原生选择器用 `replay.py` 重提，配置按记录的来源与查询参数复跑。复查输出到独立目录，机制结论只维护在案例中。
