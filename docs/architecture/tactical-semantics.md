# Tactical 目标语义与实现缺口

本文规定 Tactical 应表达的玩法语义，并记录尚未达到这些要求的地方。领域划分与纯状态契约见[总体架构](ARCHITECTURE.md)、[函数式内核](functional-core.md)；本文不以当前代码、测试或原生客户端的内部结构代替目标规则。

## 范围与依据

- ArkBattle 面向通用明日方舟战斗语义，包括普通关卡、干员、敌人和装置的战斗机制。卫戍协议是当前实现重点，不限定 Core 的能力边界。生息演算、保全派驻等特殊模式及船运寻路暂不考虑；PRTS 列出的全部模式和特殊指令不自动成为本项目的实现清单。
- PRTS 的[仇恨](https://prts.wiki/w/仇恨)、[数值范围](https://prts.wiki/w/数值范围)、[异常效果](https://prts.wiki/w/异常效果)等页面注明适用版本。目标优先采用可观察的规则；精确常数、历史溢出和注明存疑的分支需核对版本，不直接固化为长期契约。

大语义遵从官方，小差异从简：显著改变目标、命中次数、技能状态、累计数值或胜负的差异应核对资料或客户端；中间顺序先说明实际观察它的业务；普通一个 Tick 左右的响应差异采用简单、确定的约定；纯工程中间过程不增加机制。固定 Tick、函数式状态传递、RNG 实现、缓存和文件组织属于项目选择。

用户明确选择的玩法差异以对应项目规则为准。弱点伤害允许两个候选各自执行带 Hook 的完整计算，接续较高结果的状态后实行一次；这有意区别于官方理论试算，不以恢复官方比较规则为修复目标。详见 [Vitality / Damage 设计](vitality.md#2-弱点伤害的项目规则)。

healFree 只限制治疗目标选择，明确 Ref 的 Healing 不重新检查选中限制，已选中后获得限制不撤销本次治疗。这个项目政策有意区别于官方 HEAL_FREE 同时影响选中和接收的组合；真正的治疗取消通过 Receiving Hook 表达。详见 [Healing 项目政策](vitality.md#41-治疗不可选中是项目选择)。

主表对照目标规则列出当前支持范围、内容缺口与待核对问题。基础契约见对应领域文档；部分基础可用不代表内容、调用链及交互已经完整接入。测试预期应来自明确的玩法规则。

优先级是影响与依赖顺序，不是工时：**P0** 为基础战斗结果或完整链路的关键条件，**P1** 为常见机制和已确认结算缺陷，**P2** 为特定内容扩展或需要案例收敛的边界。缺失本身不等于需要新增 Capability。

## 子系统职责

| 子系统 | 职责与支持边界 |
| --- | --- |
| Battle | 同步接续领域结果，保存执行进度和 UI 事件；完整 Tick 成功后返回状态。终局由外层裁定，当前完整模式规则尚未接入。 |
| Battlefield | 保存不可变实体、空间与关系事实，维护存储及索引一致性；Blocking 的时序操作与同步通知由完整战斗操作结算。 |
| Unit / Capability | Unit 组合所需能力；能力提供自身的静态规则、运行状态、查询、声明最低宿主能力的 Change 工厂与完整结算。 |
| Contribution | 提供带身份的不可变泛型候选与 resolve 有效来源选择；领域 Change 通过 common/collection/entries.ts 维护登记，载荷求值与归并归所属领域。 |
| Hook | 接入所属领域的明确阶段；领域决定顺序和本次裁决，具体内容接续返回状态。 |
| Effect | 保存宿主附着实例、私有数据、覆写与生命周期；具体 Definition 组合 Capability 操作。 |
| Targetable / Targeting | 前者承载固有与动态受选限制及嘲讽贡献；后者提供资格谓词、显式空间判断与比较器，内容通过 Query、TopK 和 RNG 组合选择。见 [类型设计](targeting.md)。 |
| Action / Skill | Action 保存行动过程；Skill 保存技力与激活进度。释放、耗弹、回复、结束分别在明确业务时点发生。 |
| Locomotion / Route / Navigation | 分别处理运动、行动脚本和可通行路径；行动类型、寻路方式、阻挡模式不互相代替。 |
| Projectile | 已发射后的独立执行实例；Definition 解释私有 state，按内容保存目标、样本、命中历史和运动进度，并决定命中和终止策略。 |
| Deployment / Card | Deployment 管费用与部署操作；Card 管跨实例的私有 state、供给、费用惩罚和冷却；Deployable 管场上部署属性。 |
| Schedule / Predefined | 分别管理出兵／关卡动作进度，以及预置定义与运行实例的绑定；开场 Unit 使用 initiallyPresent:true 的预置项，出现时直接复用 Unit 初始化与登记。 |
| Data | 将原始资料与本次静态配置转换为规范化数据，可以静态建图、组装定义并调用已有工厂；不自行实现战斗机制程序或结算运行中的状态。 |
| Content | 根据规范化数据构造完整 Definition，提供具体行为及初始化程序；运行事实由 Core State 保存，程序由 Core 调用。 |
| Meta / 模式规则 | 通过 Battle 输入、当前状态和事件接入外层；经营、回合及完整模式结果反馈尚未接通。 |

## 待完成工作的补充说明

1. **回收事实与实际来源分开验收。** 通用串行恢复已经保留每次归队份数；是否追加时重置、是否并行恢复、是否与使用冷却关联仍按真实来源选择，不从某种已存在的枚举或测试推导原生规则。
2. **方向和手动资格不等于全部内容已接入。** 本次朝向与手动撤退 Rule 已有通用入口，具体限制、自动部署与术语移动仍应由内容组合，不增加通用权限系统或强制所有 Unit 有方向。
3. **攻击 SP 的基础入口不代表连击全覆盖。** 当前首次释放入口可用于普通攻击；每段伤害不自动等于一次攻击，必须用真实多次攻击和剑豪例外分别验证。
4. **术语移动包含完整离场与重新部署。** 特殊撤退—再部署需要结束和重新进入、Buff / Skill 初态、HP 响应及失败后继，属于待接入的完整业务，不能只替换空间坐标。
5. **低速攻速、回调微时序不先定为错误。** 当前基础 ASPD 下限 20 与间隔计算下限属于不同阶段；范围覆写是否使更低速度可达需另查。父子结束、满 SP 时的细微余量和单 Tick 响应也先证明实际影响。
6. **功能缺失与架构问题分开。** 五型元素、地形、复杂弹道、特殊异常和更多角色可以按代表内容扩展；是否需要新的状态或接入点由真实执行链路决定。

## 普通索敌的内容缺口

Targeting 与 Targetable 的查询组合和限制 API 见[领域设计](targeting.md)。以下事实与内容尚未接入普通仇恨排序；锁定后的命中资格另按内容确定。

### 仇恨事实与普通排序

嘲讽的基值与动态贡献归 Targetable。当前创建流程的 UID 表达入场先后，后入场优先直接按 ID 比较，不额外记录入场时间或序号。路线剩余路程由 Route／Navigation 提供只读查询。仇恨是排序公式，不保存为 Targetable 或 Unit 状态；具体内容选择入场或路线等优先政策，不能通过当前阵营推断。

每次比较读取当前有效嘲讽及所选规则需要的事实，不维护原生式仇恨缓存或部署计数。distance 明确表示几何距离，不能将它改名为普通仇恨。

### 弩手锁定后的阵营检查

Allegiance 保存单位当前阵营。areHostile 直接接收 Unit & Allegiance，按 PRTS 主观阵营表判断；目标查询通过显式资格谓词选择阵营，限制用途由所选标准政策或 Targetable 查询声明。

当前[弩手弹道](../../src/content/enemies/crossbowman/action.ts) 通过 tracking.hit 直接尝试锁定目标，检查目标仍为 PRESENT 且 HP 大于零，不重新检查阵营。锁定后是否重新检查阵营、读取哪个阶段的阵营事实，需要按具体弹道机制核对；这与发射时的 Targeting 请求属于不同业务时点。依据：[PRTS 选择器](https://prts.wiki/w/选择器#目标阵营（targetSide）)。

## 待核对事项

- 具体内容的普通仇恨及特殊优先组合，按上方事实与对应机制接入，不从可组合接口推导内容已经完成。
- Action 重置、前后摇的速度缩放、锁定取消与 SP 时点：以代表内容和已存在的官方调用链收敛，不依据所有 Action 看起来相似就统一处理。
- 同组禁用实例是否继续占覆写位置、父子结束回调顺序：按具体 Buff 的可观察业务核对；某个内容的保留行为不能推导为所有内容的规则。
- 元素免疫的恢复边界：当前判断来自 PRTS 文义，尚未补官方客户端动态证据。
- Card 的真实来源政策：部分 OnRecycle 状态转换的 Reset、暂停来源组合、并行恢复与特殊退出时点尚未闭合。共有一次机会由来源保存，手牌单 Ordering 接口不预设多来源竞争或退出恢复。
- 复原、免死、负生命和死亡通知：已有部分结构，需要代表内容确定统计、成功回调、消耗和最终离场边界。

## 覆盖完成标准

一项机制的完整覆盖要求：目标规则有可核对依据，实际调用链已接入，代表性正常与关键交互场景可验证，历史输入／快照保持不变，正常拒绝与失败 Tick 的边界正确。解析器分支、接口、模板或单个孤立测试的存在均不能单独作为完成证据。普通索敌、特殊接收、部署来源、关卡结果与模式机制等领域分别按这些条件判断覆盖范围。
