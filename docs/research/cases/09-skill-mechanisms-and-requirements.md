### 2.1 SP 公式与计时器：新的客户端原生核对

DLL 与 metadata 的 SHA256 仍与上文一致。此次安装 Capstone 到 `/tmp`，重新解析 metadata v29、Assembly-CSharp／Torappu.Common 方法表与字段偏移，直接读取本机 DLL 的指令；不运行客户端，也不将普通原生分支等同于已验证的运行时 XLua 覆盖。指纹、工具来源及 31 个相关方法的指令见 [sp-calculation-20261015.json](../evidence/sp-calculation-20261015.json)。

`Entity.get_spRecoveryPerSec`（`0x180708750`）分别读取属性 14 `SP_RECOVERY_PER_SEC` 与属性 30 `SP_RECOVER_RATIO`，通过 `FP.op_Multiply` 相乘。两个属性各自按通用属性计算并应用范围：

```text
attribute = clamp(((base + Σaddition) × max(0, 1 + Σmultiplier)
                   + ΣfinalAddition) × ΠfinalScaler)
effectiveRate = recoverySpeed × recoveryMultiplier
periodSeconds = 1 / effectiveRate    （effectiveRate > 0）
```

因此自然回复速度与自然回复倍率是两项独立属性；普通直接增加 SP 不套用这条自然回复公式。属性公式的原生位置为 `Attributes._CalculateAttributeValue`（`0x18064ad80`）；默认两个属性均为 1、下限为 0，亦可对照 [数值范围](https://prts.wiki/w/数值范围)。

`SpController.OnTick`（`0x18070a1c0`）在阻回或满 SP 时直接跳过计时器更新；否则由精确周期计时器计算完成周期数，再增加相应 SP。此路径保留暂停前的计时余量。

动态修改有效速度时，`SpController.UpdateSpRecoveryPerSec`（`0x18070a670`）先用零时间更新结清旧计时器已完成的周期；有效计时器随后调用 `PeriodicTimer.ResetButKeepPastTime`（`0x181e044e0`）：

```text
elapsed = previousPeriod - previousRemaining
nextRemaining = max(0, nextPeriod - elapsed)
```

保留的是已经经过的绝对计时时长，不是周期完成比例。此前类型草案将 `recoveryProgress` 直接定义为归一化比例，不能自然保持这项行为。目标数据应能保留周期与剩余时间，或保存可等价推导它们的事实。

有效速度不大于零时，普通分支将计时器设为无效（周期和余量写为 -1）；以后恢复正速度且旧计时器无效时，使用 `Reset(period, true)` 从完整新周期开始。这与阻回／满 SP 保留余量的暂停语义不同。项目不需要复刻无效值 -1，但应保留这项可观察差异；浮点 epsilon 与约一 Tick 的响应沿用 README 的从简约定。

### 2.2 MODIFY 不隐含强制或无视阻回

`ModifySp.Execute`（`0x181041ca0`）具有独立的 `_forceFlag`（实例偏移 `0x24`），作为黑板布尔值的默认值传给 `Entity.ApplyModifier`。`Entity.DoApplyModifier`（`0x1806f1c00`）的 SP 分支明确区分：

| 操作 | 阻回 `SP_RECOVER_STOPPED` | 技力封闭 `SP_MODIFY_STOPPED` |
| --- | --- | --- |
| 普通 SP modifier，正增量 | 拦截 | 拦截 |
| 普通 SP modifier，负增量 | 不因阻回拦截 | 拦截 |
| 显式强制 SP modifier，正／负增量 | 绕过该检查 | 绕过该检查 |

原生位置：`0x1806f20ba` 的 force 分支、`0x1806f2127` 的异常 29 检查、`0x1806f2156` 的 force 分支，以及 `0x1806f2160` 至 `0x1806f21b9` 的阻回与负增量检查。自然／攻击／受击回复走 `SpController._RecoverMp`，此入口检查阻回后直接写 SP，不通过 modifier 的技力封闭检查。不能把所有资源变更按一个许可处理，也不能从 `MODIFY` 这个名字推导强制性。

PRTS 的[异常效果](https://prts.wiki/w/异常效果)与该区分一致。[森西](https://prts.wiki/w/森西#技能)的普通外部增加会受阻回影响；[掠风](https://prts.wiki/w/掠风#技能)则有明确无视阻回的回复。因而草案中的 `MODIFY(+1)` 默认仍为普通变更，需要无视限制时以明确业务参数表示。强制只影响规定的限制，不能跳过实例身份、生命周期与容量边界。

### 2.3 SP 变化报告与内容阈值的项目契约

普通可充能技能不需要独立阈值事件。公共层按具体资源业务提供 `spRecovered`、`spPaid`、`spModified`，不保留兜底的 `spChanged`；此前草案中的 `Definition.thresholds`、`State.thresholdCrossed` 及必备 `ThresholdCrossed` 类型取消。特殊内容需要检测阈值时，以相关业务的已结算 SP 报告判断，可以将同一处理器登记到多个具体 Hook，不为普通充能维护额外计数或状态机。以下是同步结算的项目约定，不声称客户端使用相同事件类型：

1. 从本次操作的当前输入读取 SP，处理许可、支付／增减和容量限制。
2. 先写入实际结算后的 SP，并形成不可变报告，再派发任何同步 Hook。内容如果依赖会动态变化的门槛，报告保留本次相关参数的采样，不能事后用最新参数重构历史。
3. 内容按需判定上行 `previous < threshold && current >= threshold` 或下行 `previous >= threshold && current < threshold`；两个数值始终来自同一份报告。
4. 嵌套操作产生自己的报告；外层后续派发继续使用原报告，不根据此刻 SP 重算、撤销或拼接外层的变化事实。
5. Hook 如需判断此刻仍达标、当前激活仍存在等资格，从接续后的最新 battle 查询。当前资格和历史事件分别表达。

例如外层回复 `9 → 11` 跨过 10，回复 Hook 中嵌套支付为 `11 → 0`，两次报告分别描述两次实际结算；外层载荷不会被重写为 `9 → 0`。因容量截断而实际未到阈值的请求，也不能被内容误判为达标。

### 2.4 回复来源、支付与充能类型的收敛

客户端的攻击回复入口是 `AbilityStandard.OnOutputAttackOrHeal` → `Entity.OnOutputAttackOrHeal` → SP controller 的攻击来源分支，覆盖符合资格的攻击／治疗输出通知；并非只依赖对敌伤害，也不将每个 Damage／Healing 结算包视为一次触发。`OnOutputAttackOrHealEachSpell` 是另一通知入口，普通 Entity 分支只通知 Buff，不在此直接回复 SP。具体连击、剑豪等例外仍按内容核对。

项目来源采用 `ACTION`，表达由行动中的明确业务点触发回复。此前提议的 `ATTACK_OR_HEAL` 仍按输出类型命名，不能覆盖项目 Action 所表达的全部行为。Action 可以表达攻击、治疗、装弹、储能等；[PRTS 异常效果](https://prts.wiki/w/异常效果)明确普通攻击限制也覆盖装弹、储能。是否受该限制与是否产生回复触发是分别确定的业务资格；这份资料本身不能证明装弹／储能必然回复 SP。具体内容在正确业务点调用 Skill 资源操作或通过公开扩展点接入，通用 Action 的启动、推进和结束不自动回复 SP，不另造输出类型枚举作为 Skill 的准入依据。

支付由 Skill 完整资源操作检查与结算，保持数值接口。Definition 保存基础数值 cost，贡献修正默认 cost；特殊发动程序可以在准备时选择本次实际 cost。全额支付可将本次采样的当前 SP 作为数值，和形态采样使用同一事实。无需为了固定数额／全部 SP 单独提供通用 `Payment` 联合类型；`PAY` 仍作为明确资源操作语义保留。

普通可充能是扩大容量；基础门槛／单次消费为 C、容量为 N×C 时，可释放次数从 SP 派生。蓄力的额外形态与支付方式由内容决定，两者共用资源和激活机制，不新增公共 `CHARGE` 类型或充能状态机。

特殊达标历史仍是实际需求：如薇薇安娜 S1 达标后改变攻击范围，SP 下降不自动退出直到下一次技能结束。这类内容用持久私有状态 S 记录事实并管理相应 Effect；不能将所有内容仅按发动时的当前 SP 重建。Activation 的 ACTIVE／ENDING 属于终止重入契约，与是否充能无关。

| 号角 S2 | 弹药阈值触发过载；二次触发可进入倾泻并暂时禁止再次关闭。倾泻结束／中断后仍有余弹时可能回到原状态。 | 激活中存在有条件的操作、阶段转换与暂时限制；二次操作不等于 stop。 [号角](https://m.prts.wiki/w/号角#技能)、[弹药倾泻](https://prts.wiki/w/特殊机制#弹药倾泻) |
| 蕾缪安 S3 | 持续锁定并追踪目标，目标退场后标记留在原处；结束后依次轰炸，使用结束时缓存的攻击力。 | 需要持续记录、结束时采样与结束后的独立执行；Skill 结束与全部产物结束不相等。 [来源](https://prts.wiki/w/蕾缪安#技能) |
| 被动 | 部署触发的被动可以有限持续；慕斯又属于按攻击条件工作的特殊被动。 | 被动不是“无消耗、无限持续、自动启动一次”的唯一模板。 [止颂 S2](https://m.prts.wiki/w/止颂#技能)、[慕斯](https://prts.wiki/w/慕斯#技能) |

Skill 结束后的输出不自动证明宿主离场后也继续。例如蕾缪安的轰炸在宿主死亡／撤退后的完整规则，本轮尚未确认。产物是否绑定 Skill、Unit 或其他生命周期，应按实际内容确定。

### 3.1 资源事件的接口评审要求

仅有资源数值变化、`activated`、`ended` 无法清晰表达上表中的业务观察者。接口按已结算的业务事实收窄，不保留 `spChanged`、`ammoChanged` 一类兜底通知：

| Hook | 对应事实 |
| --- | --- |
| `spRecovered` | 通过回复操作实际获得 SP，保留回复来源。 |
| `spPaid` | 成功支付 SP，不能由一般的负增量推导。 |
| `spModified` | 直接 MODIFY 操作实际改变 SP；不额外接收 RECOVER 或 PAY 的通知。 |
| `ammoConsumed` | 实际消费指定数额的弹药，包括允许负余量的消费。 |
| `ammoReplenished` | 普通补弹操作实际补入弹药；对应补弹累计额度政策。 |
| `activated` | 成功创建本次 Activation。 |
| `ended` | 本次 Activation 结束。 |

一次资源结算派发其对应的具体 Hook，不再追加兜底变化事件。载荷按该项业务定义类型，保留实际数额、前后值及所需来源，而不要求每个观察者重新从通用请求联合中筛选业务。其他直接弹药增加的操作及通知名称随其业务接口确定，不能混入普通补弹累计额度或消费。增加资源操作也不自动要求添加没有观察者的 Hook。

不因数值下降就推导发生了消费，也不把结束时丢弃剩余弹药派发为消费。普通正向 SP MODIFY 的阻回许可与其事后通知是两项职责；受到回复限制不意味着同时派发 `spRecovered`。

报告应保留本次 Activation 的 typed Ref、请求语义与数额、结算前后的不可变弹药快照；初始预算、剩余量以及补弹政策涉及的累计事实按实际需要采样。先写入本次结算结果，再派发 Hook。嵌套补弹或消费产生独立报告，外层报告不能改用最新值重建；后续耗尽检查需要从最新 battle 重读同一 Activation。消费已经结算时，不因 Hook 结束该 Activation 就撤销既成事实。

其他单位可以通过公开 Hook 登记接口观察目标的具体弹药业务，不要求 Skill 识别具体观察者或增加中央事件转发。消费通知保留数额，不要求公共层为每一发拆成一次独立数值提交；具体多次响应的时序仍按真实可观察业务确定。

弹药阈值可以从已结算的报告判断，暂不增加通用 `ammoExhausted` 或阈值注册表。TIME 的自然流逝通过 battle.tick 查询，到期通过 `ended` 观察；没有实际观察者时，不为每个 Tick 或每次持续预算修正预置新的 Hook。

## 4. 调度与范围

[卫戍帮助](https://prts.wiki/w/卫戍协议/帮助#作战阶段)明确，模式会自动操作原本的手动技能，具有自己的操作冷却和普通／特殊策略，也存在主动关闭的特殊策略。因此，技能自身触发类型与模式控制策略是两项需求。不能仅把 MANUAL 改为 AUTO 后按 SP 足够启动。既有项目的明确偏离继续按原约定处理。

[敌人技能说明](https://prts.wiki/w/矢量战术装备#技能)与既有官方原生证据记录了：各技能的首次／后续冷却、施放期间暂停、绑定模式下推进、优先级与同层随机选择，以及另有 SP 条件。敌人技能的触发冷却不等于普通攻击周期。这里只要求架构能够组合这些事实；是否复用干员 Skill 的同一实例模型，应在后续设计中评估。

## 5. 从机制归纳的需求

以下是设计约束，不声称官方内部采用相同模块或接口：

1. SP 的值、自然回复进度、上限、门槛、支付与许可可以分别表达；动态贡献和特殊回复规则有明确归属。
2. 允许技能通过攻击、受击、部署、指令、时间及其他真实业务接入；所属领域提供事件契约，Skill 处理自己的机制。
3. 需要保存跨多次启动的技能状态与本次执行状态；特殊跨部署资源另有持久载体。
4. 触发、开启、动作 casting、持续效果与结束是可区分的事实；具体技能决定它们的关系，不预设全技能统一阶段机。
5. 正在生效的技能可接收有资格限制的操作；内容可以改变阶段、付费、发动动作或结束。
6. 持续时间、弹药、攻击完成与阈值转换是可组合的内容机制；通用层不将其中一种写成所有技能的结束规则。
7. Skill、Action、Effect、Projectile 按明确生命周期依赖清理；结束业务可以创建独立后继。终止、依赖关闭与收尾一次仍由所属领域保证。
8. 继续遵守同步重入与状态接续契约：返回后需要当前事实时重读；已采样数据按约定保留；已进入的程序不会因外层对象终止被自动撤销。
9. 模式自动操作、敌人技能选择和具体攻击执行各有职责；这些需求不要求引入统一 Resources、Context 或中央调度注册表。

## 6. 尚未确定的具体行为

- 断罪者等具体强力击何帧扣 SP，以及前摇中目标失效／中断时是否返还，尚不能统一归纳。冬时 S1 有索敌失败返还的特殊处理，不能推广。 [冬时](https://m.prts.wiki/w/冬时#技能)
- 攻击回复与释放、未命中、失效弹道、多目标的完整组合，及受击回复在闪避／屏障／抵挡后的准确资格，需要相关链路证据。
- 动态改变 SP 需求时的现有 SP 换算、容量裁剪与自然回复进度变更算法，尚未完成客户端核对。
- 来源退场后，具体持续／延迟技能输出的退出规则要逐例确认。

### 本次覆盖审查揭示的边界

1. **发动资格的例外。** [止颂 S3](https://prts.wiki/w/止颂#技能)允许在部分异常状态中发动并清除状态。`allowsActivation` 若只作为附加否决条件，不能覆盖通用入口此前已经作出的硬拒绝。发动协议需要使常规异常限制具有可配置的例外；实例身份、宿主存在及必要生命周期约束仍由完整操作维护。不因此引入任意优先级的许可仲裁。
2. **弹药补充历史与加成资格。** 普通补弹的累计额度需要独立事实；自身弹药增加与普通补弹分别结算。图耶案例需要保留不同加成的资格，但不因此证明项目必须再造一种持续状态机。具体类型位置待定，不能仅用 `sustain.type === "AMMO"` 代替所有资格查询。
3. **跨部署资源。** [玛露西尔](https://prts.wiki/w/玛露西尔#天赋)的魔力在整场战斗继承，并涉及待部署区回复。场上消费可复用资源操作，完整行为还需要 Card／队伍等跨部署载体，不能声称单个 Unit 的 `skill.data` 已经涵盖。
4. **暂停持续计时。** [Fever](https://prts.wiki/w/术语释义#Fever)会让进入前正在持续的技能暂停计时，并在结束后恢复。只有绝对 `endsAtTick` 足以表达固定流逝的 TIME；若纳入该机制，还需要显式的暂停／恢复事实和操作，不能用反复延后一 Tick 隐藏这个区别。Fever 的共享资源属于队伍机制，不应成为 Skill 的通用私有字段。

Action 侧还需在 Operations 设计中确定普通行动的准备、实际释放与完成等公开业务点；不能将现有 `beforeRelease` 当作它们的统一替代。Skill 程序负责在这些业务点组合公开接口，Action 核心不据此了解具体技能。

这些未知限制具体策略的定稿，不妨碍先分开已经证明不同的概念。下一步 API 设计应以本页需求和代表性轨迹验收。
