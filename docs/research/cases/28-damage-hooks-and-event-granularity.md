# 伤害扩展时点与事件粒度

研究日期：2026-11-03；项目基线 `f5306f4`。问题是实际玩法需要哪些内容介入／观察机会，不按原生函数或现有项目 Hook 数量倒推需求。本轮只研究与提出接口依据，不修改运行代码、测试或既定结算政策。

## 1. 结论

需要区分**公式输入、来源输出、目标接收、实际 HP 应用、成功应用后的事实**。此外，成功闪避是接收中的即时结果，击杀／死亡是生命结束事实；它们不能用整轮攻击完成、Damage 返回或 HP 差统一替代。

这是语义需求，不是一张必须逐项实现同名公共 Hook 的清单。具体攻击直接编排多段 Damage、EP 和 Effect，独立登记的天赋／装备才需要相应的观察或干预契约。一次攻击、一次释放、一个命中目标、一段伤害、一次公式试算分别计数。

“吸血”“受伤时”“攻击时”都是容易混用的文案。上表分别依据时点备注与调用链，不按中文动词直接归类。例如武者输出回复与咒愈师成功后回复不是同一个时点；止颂受击增攻不要求成功受伤，也不能因文案含“后”就归入目标应用后。

## 3. 有时序依据，但不应直接增加独立公共 Hook

| 项目 | 本轮判断 |
| --- | --- |
| 普通受击 SP 的开始时点 | 当前 native 在 Buff 接收列表前检查取消和 ignoreForSp，再回复 SP。因此初始零与随后被盾抵挡有不同结果；项目入口 Rule 拒绝另按既定契约，不据此概括原生全部无敌路径。需要保证此顺序；可以由接收流程保留的首项或既有接入点实现，尚不能据此要求独立 Started API。 |
| 攻击判定与释放 | [山](https://prts.wiki/w/山#天赋)的概率按攻击判定，不能每段 Damage 或弱点试算都抽一次；攻击回复 SP 还区分普通连击与剑豪二连击。机会属于攻击业务。既有直接程序／能力接口能接入时，不据此新增通用全局释放 Hook。 |
| 弹道命中／本击前置程序 | 妮芙 S1 的额外 HP 段可由命中程序先调用 Damage，再执行主 Damage。没有独立被动的不可替代需求时，直接顺序不必包装成公共 beforeDamage Hook。 |
| 接收后、HP 写入前的来源程序 | 原生事件 61 在此安装妮芙延迟监听。它证明调用位置，尚不足以独立证明项目需要一个任意公共“最后修改”节点；先按具体内容检查其可区分结果。 |
| 计算后清理 | PRTS《事件》将原生 AfterCalculate 用于撤销计算期间的临时数值。采用本次公式输入表达后，未找到仍必须广播独立清理 Hook 的样例。不可由这次有限检索推断所有游戏版本都没有其他用途。 |
| 覆盖全部结果的 Completed | 本轮未找到实际内容必须统一观察拒绝、取消、目标失效和成功的样例。操作返回 Outcome 与成功应用后通知应先分别说明，不能因现有 Completed 存在就自动保留为必需接口。 |
| 闪避成功／抵挡成功 | 成功闪避的独立观察需求已证实；抵挡只确认原生即时通知，本轮不据此要求公开节点。成功通知位于判断成功处，不是整次 Receiving 返回后才批量补发。 |
| 妮芙的 0.1 秒监听 | 是内容的延迟检查，Effect 已能表达。EP 同步结算，不以此证明通用 Damage 要增加延迟。 |

以上是必要性审查结果，尚未决定删除哪些现有接口。特别是[现有 Vitality 文档](../../architecture/vitality.md)的弱点双分支计算、接收／死亡与 Completed 已有项目约定，不能被本调查静默改写。

## 4. 数据与时序约束

- 攻击判定频次由攻击程序确定，公式回调次数不能代表命中／伤害次数。当前 native 的 rawValue 参考计算还会再次调用目标计算程序；原生弱点的无事件试算不重新派发计算事件。项目既定的双分支完整 Calculate 及分支状态接续仍按 Vitality §2，不由此修改。
- 本段 HP 伤害类型、是否攻击本体／Buff 附加、施加途径与参与哪些接收程序分别说明。不能从来源职业、阻挡状态或当前 Action 猜测已经发射那一段的性质。也不在本轮预定一组照抄原生的 flags。
- 计算量、接收量、实际 HP／屏障变化、取消原因、来源及击杀归属是不同事实。咒愈师治疗与妮芙 EP 都不能无条件按 hpLoss 计算。
- Receiving 可以同步治疗；真正扣血读取返回后的最新 HP。前置治疗与扣血后治疗的致死结果不同，不可机械换位。
- 对本次已提交结果的通知不追溯撤销该次应用；观察者可以继续发起独立业务。成功免死的专属后续不等于所有伤害都新增广播阶段。
- 当前项目已选择 hpApplied 在死亡确认之前，普通 native 的死亡清理可先于应用后通知。本轮研究不改变这项项目约定；死亡确定、业务清理与物理回收仍分别处理。

## 5. 证据范围与未决项

本批[取证与资料登记](../evidence/damage-hook-needs-20261103/README.md)保存 9 个新增接收／免死节点的当前方法区间、六个既有模板的当前解码及 PRTS 页面／章节／日期。通用计算、HP、死亡链复用案例 27；弱点的历史证据保留其旧指纹，不将旧地址与新客户端混用。

模板本身不证明所有当前角色／模式仍使用它。当前 PRTS 普通模式泥岩说明单一 Buff 持续补充层数，旧案例 03 的 shield_a 则会 Finish；本批确认旧样例模板仍在 Holder 中，但没有重做当前全角色可达链。只据两者共同支持“抵挡后仍能回复／修改内容状态”，不把实例销毁策略合并为一个普遍规则。

未闭合：所有零值、无敌、完全吸收下各观察者的资格；不同来源失效、重生与全部伤害旁路；抵挡的独立观察者；全部暴击与弱点的相对顺序；弱点试算是否计入逻各斯附加项的历史 native／PRTS 差异。本轮不以测试或未核实的字段名称填补这些缺口。

## 6. 目标前置与来源输出能否交换

2026-11-03 定向核对一个具体问题：能否找到真实、正常可达的内容组合，证明必须保留原生的目标 BeforeApplying5 → 来源 OutputModifier8／OutputDamage11，而不能把来源输出放到 Calculate 末尾、目标前置放到 Apply？只比较这两个位置，不把妮芙前置判断后移、HP 后置 EP、目标接收6／10与来源输出的差异混入。

**本次有限查找没有确认这样的实际反例。** 这不是全游戏顺序可交换的证明，也不是删除所有目标前置程序的依据。必要材料、四个新增索敌方法、精确配置与复跑入口见[输出顺序证据](../evidence/damage-output-order-20261103/README.md)。

| 候选 | 核对结果 |
| --- | --- |
| 浮空信件的前置计数与来源附带沉默 | 实际计数 Buff 的 `isSilenceable=false`，已核对 event5 也没有沉默条件；不能声称先附带沉默就能抑制本击计数／传送。复用 EP 事件补查的真实 Prefab 与完整模板。 |
| 蒂比自动规避与来源输出时回 SP | 所核对的是 S2 `tippi_s_2[trigger]`，位于 Applying6，不是 Before5。原生顺序5→来源11→接收6本就让来源输出先发生，不能用于证明5与11的交换冲突。[PRTS蒂比](https://prts.wiki/w/蒂比#技能)和[绽放](https://prts.wiki/w/绽放)的说明没有改变这个事件位置。 |
| 羽毛笔 S2 重算与禁闭所的前置清零 | 两个数值动作看似不能交换，但普通输入资格排除了冲突位置。禁闭所本体的 `_hitRangeId` 与前置检查同为 `x-5`；羽毛笔 S2 Selector 没有豁免 hitRange，范围外目标在选取时被拒绝；范围内又不执行清零分支。不能仅凭羽毛笔自身攻击范围覆盖斜前方，就认定该伤害能进入结算。 |
| 羽毛笔与心烛最低伤害 | [隐德来希S3](https://prts.wiki/w/隐德来希#技能)的心烛只接受其对应攻击，不能把羽毛笔输出重算直接配在这项限定目标上；本次没有寻找强行改变阵营或来源的特殊组合。 |

禁闭所是 `trap_317_ubprison`，敌方默认类装置。其本体 PathID `-8720332516268970448` 的 `_commonAbilities` 引用 `-664377713333506512`，后者实际挂载 `ubprison_p[check_range]`，黑板 `modify_scale_zero=0`。羽毛笔 S2 Attack `2831199944281353299` 引用 Selector `-164417716366349229`，`_ignoreHitRange=0`、`_alwaysIncludeTarget=0`。原生 AdvancedSelector.ValidateTarget75508 进入基类76395，基类在 `0x180a4195f` 调目标 slot135；Trap.IsInHitRange78848 检查相应来源格是否属于 hitRangeGrids，失败即拒绝。因此这是实际索敌链的排除，不是把不存在的伤害请求交给两种顺序试算。

另复核了 Before5 返回后的取消门：ApplyModifier67665 在 `0x18072163d` 只对取消原因值5提前返回；其他取消仍可能继续来源8／11，具体来源程序再按自己的资格响应。存在取消动作、或看到两个操作在数学上不能交换，都不足以证明实际来源输出会被这个门阻止。本次未将相关取消模板与正常可达的来源副作用闭合为另一实际反例。

查找范围止于当前模板候选、上述具体组合和必要资格链。未核对所有客户端特化、动态位移、强制目标输入或活跃 XLua，也不人为制造这些场景作为默认架构的前提。当前没有新增要求来推翻项目的 Calculate／Apply 边界；最终 Hook 契约仍按已确认业务语义设计，而非按原生事件编号逐项复制。

**项目决策（2026-11-03，用户确认）：** [Calculate 负责输出计算，Apply 负责目标接收](../../architecture/vitality.md#1-calculate-与-apply-的语义边界)，适用于 HP／EP 的伤害与治疗，不再以复刻原生 Hook 时序为目标。公式与最终输出修正归 Calculate；本笔输出的目标前置、伤判、资源提交与后置归 Apply。弱点的两次 Calculate 不派发本笔受击响应，仅选中结果执行一次 Apply。以后发现影响重要玩法的具体内容差异时，针对该机制处理；本次未找到反例不等于证明所有原生程序可交换。
