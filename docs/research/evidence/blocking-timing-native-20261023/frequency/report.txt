So an eligible attempt consumes readiness even if the later business checks reject acquisition or find no targets.

Equivalent pseudocode:
    SearchBlockee(owner, force):
        if !force && !ticker.isReady:
            return
        ticker.Next()  // resets only if currently ready
        if owner is ineligible or full:
            return
        candidates = searchAndSelect(...)
        for candidate in candidates:
            AddBlockee(owner,candidate)
There is no repeat-until-stable or multi-search loop; its loop is selected targets within this one search.

For one normally updated eligible owner, attempts occur at updates 0,3,6,9... after initial ready state. Counts after each ordinary eligible update:
    update 0: Tick 0->0, search, Next 0->3
    update 1: Tick 3->2, ordinary attempt returns
    update 2: Tick 2->1, ordinary attempt returns
    update 3: Tick 1->0, search, Next 0->3
Call it every 3 eligible fixed logic updates; don't call it every 3 rendered frames. Whether ordinary updating is skipped because the actor is dead or a special override applies affects the count.

5. What force does to next ordinary search
- count==0: force bypasses check; Next changes 0->3. It consumes the current ready slot.
- count==1/2/3: force bypasses check; Next returns false and leaves count unchanged. It DOES NOT restart the 3-update countdown.
- ordinary search just ran (count=3), explicit force later in same logic Tick still searches; count remains3.
- explicit force before normal owner update, count=1: force searches without resetting; owner Tick 1->0 then ordinary search also occurs.
- explicit force before normal owner update, count=0: force consumes ready ->3; owner Tick ->2; ordinary search is skipped.
- two explicit force entrances in same Tick are both accepted on alive owner. There is no global once-per-Tick constraint. This is a control-flow consequence, not a claim that a particular two-content combination has been run in the game.
- repeated artificial calls to Character.OnTick would advance this count, but that is not evidence the normal scheduler does so; normal update count must be read from scheduler, not inferred from public callability.

6. Different owners and lack of a native global Blocking fixed-point phase
Each owner owns its own ticker/manager. Different blockers each make their independent attempt during their update. A battle frame can have multiple searches across blockers by ordinary design. They are not repeated global rounds: owner A's search does not cause all earlier owners to search again.
The native manager contains no worklist, convergence loop, or global 'run until no new relations' phase.
One search may acquire several targets from its selected list. That is one selected-candidate iteration, not a second search from updated world state.

    m_blockCnt int at +0x57c
    m_cachedCheckBlockable at +0x580
Native path:
    0x180ab000b if m_checkedBlock && !force: return
    sets m_checkedBlock=false and m_blockCnt=0

    applies own checks/filter (not BlockManager.SearchBlockee)

    at 0x180ab0360 sets m_checkedBlock=true on successful path
This special object's normal search can be one-shot until another change/reset; force can redo it. It does not demonstrate ordinary Character search requires multiple global rounds. Its own complete special OnTick and content reachability are beyond ordinary-blocking scope.

8. Consequence for Stronghold architecture (inference, not native identity)
- Native directly supports independent release/maintenance and ordinary acquire entrances.
- A project-wide ordinary Blocking Step once per Tick is a reasonable chosen simplification, but not a literal reconstruction of native's per-owner period or native interleaving with each Unit's update.
- Keep an explicit acquire operation available to contents which require immediate search after pull/action. Do not implement these as a rule that every Unit update triggers global acquire, and do not impose a broad once-per-Tick guard that suppresses explicitly requested searches.
- No evidence here supports two global Blocking passes merely because native has ordinary plus explicit search calls. The required relative position of the one ordinary Step comes from complete movement-order investigation.
